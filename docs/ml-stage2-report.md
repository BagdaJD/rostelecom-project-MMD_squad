# Этап 2: Data Pipeline, NLP и Scoring

Дата проверки: 25.10.2026. Ветка: `feature/ml-stage2-validation`.
Итоговый статус: **PARTIALLY_READY**. Собственная реализация проверена на реальных
Excel, ФНС, CPU E5 и отдельной PostgreSQL/PostGIS. Независимой экспертной разметки,
подтверждённого покрытия оператора и исходов продаж нет. Измеренное качество NLP
и вероятность продажи не заявляются. Начать проверку можно по
[короткой инструкции](ml-quick-check.md).

## Реализация и исправления

Реализована цепочка Excel/FNS → нормализация → matching → признаки → правила или
гибрид E5 → эвристический scoring → PostgreSQL → сохранённые ответы FastAPI.
HTTP не скачивает модель и не запускает тяжёлый inference. Исходные файлы не меняются.
Проверяются контрольные цифры ИНН/ОГРН, конфликт идентификаторов, дубли,
происхождение и повторяемость загрузки. Пропущенные значения сохраняются как NULL.

На этапе 2 добавлены потоковый аудит полного ZIP, региональный JSONL, проверка
завершённости аудита перед объединением, review-only поиск инициаторов,
измерение RSS, диагностика NLP/scoring и обычный/слепой Excel для экспертов.
Генератор объединяет идентичные рекомендации обоих методов и включает отказы.
Evaluator принимает только заполненные ручные оценки, проверяет целостность
таблицы, раздельно оценивает dev/test и не создаёт метки из предсказаний.

Исправлены подтверждённые технические проблемы:

- PostgreSQL отклонял запрос выручки с 70 000 параметров при лимите 65 535;
  теперь lookup выполняется пакетами по 10 000. Регрессионный тест использует 70 001 ID.
- Для каждого импортируемого объекта выполнялись поиски без индексов по
  `CompanyMatch.source_record_id` и `Company.ogrn`; добавлены отдельные миграции.
- Конфигурация scoring загружалась для каждой компании; теперь один раз на пакет.
  JSON записывается потоком вместо создания дополнительной большой строки в RAM.
- Полный SQL-прогон выявил замедление построчных lookup: BitmapAnd просматривал
  около 40 тысяч записей источника для одного hash. Импорт компаний, источников,
  provenance и company snapshots переведён на ограниченные пакеты до 1 000 записей.
  Поиск источников использует ограниченный набор hash. Проверки конфликтов,
  раздельность объектов без идентификаторов и управление транзакцией сохранены;
  результат сравнен с прежним загрузчиком на PostgreSQL, включая границы пакетов.
- Версия E5 зависела от расположения локального кеша; теперь определяется
  семантической конфигурацией и ревизией модели.
- Четыре знака покрытия скрывали семь пропущенных муниципалитетов; теперь
  шесть знаков и отдельные точные счётчики пропусков.
- Переносимый `pg_ctl` на Windows удерживал захваченные pipe; запуск сервера
  отделён от pipe, без установки службы.
- Старые integration-тесты могли использовать обычную DATABASE_URL и удалять
  компании; теперь обязательны отдельная БД, marker и внешний rollback с savepoints.

Добавлены миграции `20261024_ml_details`, `20261025_ml_source_match_index`,
`20261025_ml_ogrn_index`. Первая сохраняет старые строки, добавляет nullable
NLP metadata и разрешает NULL score. Откат NOT NULL запрещён при наличии NULL.
В репозитории нет исходной миграции создания всей схемы: подготовка новой БД
описана в [инструкции](ml-pipeline.md). Рабочая БД не изменялась.

## F. Ограничения и действия команды

В собственной области нет известных критических дефектов по выполненным
проверкам; ограничения качества данных и внешней интеграции остаются:

1. Эксперт заполняет обычный либо слепой XLSX. Только после этого возможны
   честное сравнение методов и выбор порога на dev с единственной оценкой test.
2. Владелец данных предоставляет проверенные ИНН инициаторов, финансовые ряды,
   подтверждённое клиентское присутствие и исходы продаж. Без них нет trained
   модели, вероятности продажи или достоверных «белых пятен».
3. Владелец frontend обрабатывает nullable revenue/growth/presence/probability,
   показывает `presence_status`, различает explicit/inferred и выводит объекты
   без координат списком. Изменения frontend вне области этой задачи.
4. Владелец общей БД проверяет и применяет миграции в своём окружении;
   владелец worker подключает готовые пакетные функции при необходимости.

Для демонстрации доступны CLI/JSON, объяснимые потребности, эвристические
рейтинги и API на отдельной БД. Готовность всей пользовательской системы
зависит от указанных данных и компонентов, поэтому статус PARTIALLY_READY.
